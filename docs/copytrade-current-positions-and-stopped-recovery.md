# 停止状态对账与一次性复制当前仓位

## 停止交易员的历史执行责任

交易员更换执行账户后，历史执行责任仍可能归属原账户。账户互斥检查保留这部分责任，避免另一交易员接管尚有未决订单的账户。历史 `FILLED` 回执缺少成交数量时，终态时间不能单独证明订单已完成。

“核对归档条件”现在会读取持久化的执行账户声明，使用原账户凭证查询原订单，校验订单身份并补齐成交数量和成交时间。成交证据复用现有修复审计与逐单去重入账。该路径不会提交或重放订单。

在历史订单结果明确、原账户最新快照证明无持仓、普通挂单和条件挂单后，事务再次核验生命周期代次、账户身份、当前配置和并发运行状态，释放残留托管责任。配置账户与原账户不同时，还会检查配置账户的归档条件。凭证缺失、查询失败、身份不一致、真实持仓或挂单都会保留相应阻塞并返回具体原因。

保存执行账户变更也会在同一事务中检查原账户责任。历史日志、订单、成交审计与盈亏数据保留，正常处理使用归档，不需要物理删除交易员或日志。

## 一次性复制

在新建或编辑交易员的 OKX 领航员配置区开启“下次启动时复制领航员当前仓位”。默认关闭，保存只登记请求。运行中的交易员须先停止才能登记新请求。

只读预览展示多空方向、领航员杠杆及保证金模式、领航员均价、执行参考价、价差、预计名义金额和跳过原因。价格优劣仅供参考，不是入场门槛。预览不初始化交易运行时，也不设置交易所持仓模式。

下次手动启动重新读取完整源仓和执行账户快照，按以下公式进入已有普通开仓链路：

`源仓当前名义金额 ÷ 领航员总权益 × 执行账户总权益 × 跟单系数`

实际数量、最小量取整、杠杆和保证金模式遵循既有交易规则。成功后，加仓、减仓、平仓、手动停跟及保护逻辑继续走普通跟单流程。

允许从未参与过的当前源仓，以及首次初始化、升级或停止恢复基线忽略的当前源仓。已跟随、主动停跟、风险退出、归属脱离、有未决订单或身份不明的源仓不重新接管。同方向存在独立手动仓时仍按原归属规则拒绝。多个源仓采用现有方向组；执行仓合并还需核实对应保证金模式下的原托管仓连续性。

## 请求与恢复边界

- 请求绑定交易员、执行账户、领航员、来源代次及手动启动代次。相同请求编号重复保存不会重复登记。
- 批次建立时一次性固化源仓范围，逐仓记录准确源仓 ID、开仓周期、方向和保证金模式。重启恢复原任务与原订单，不扩展批次。
- `copy_pending` 仅表示入场授权，不代表已经成交或拥有仓位。只有既有成交事务可以建立正式映射和托管责任。
- 逐仓任务与普通 `LEADER_TRANSITION` 开仓意图原子绑定，使用现有客户端订单幂等编号和成交入账。决策附带当前仓位复制来源标记。
- 提交前再次验证源仓身份和授权。领航员平仓、反向、换周期或复制窗口结束后，未提交部分失效；不确定的订单结果必须继续对账。
- 同一源周期只发生数量变化时，仅在确认原意图从未提交或已终结且零成交后，按最新剩余源数量更新同一任务，旧意图与收尾证据保留。已提交且结果不明时不能替换订单。
- 部分成交、余额不足、低于最小量沿用有界补齐；价格锚点采用本次执行参考价，既有补齐窗口和不利滑点限制仍有效。
- 同方向部分源仓成功后，未成交成员保留方向组的源数量基线与退出参与，但不能自行加仓或获得仓位托管权。
- 主动停止会结束未提交部分，保留已提交订单的对账责任。切换账户、领航员或决策模式会使原待执行授权失效。
- 完整快照为空时记录“无可复制仓位”。启动前置检查或完整快照获取失败时，尚未建立的请求保持待执行。
- 本地写入失败不等于源任务已完成。未提交任务可恢复同一意图；成交尚未入账的任务不会被批次结果隐藏。

## 接口与数据

跟单配置支持可选字段：

```json
{
  "copy_current_positions_once": true,
  "copy_current_positions_request_id": "客户端生成的 UUID"
}
```

旧客户端省略字段时维持原行为。配置读取返回待执行开关、请求编号和 `current_position_copy` 最近结果。关闭开关取消尚未建立的请求；重新开启使用新的请求编号。

`POST /api/copytrade/current-positions/preview` 接收 `trader_id`（新建可省略）、`exchange_id`、`provider_type: "okx"`、`leader_id`、`copy_ratio`。接口校验交易员与执行账户归属，只进行查询。

新增表 `copy_trade_current_position_requests` 与 `copy_trade_current_position_tasks`，由现有数据库初始化流程自动创建。旧配置不会自动启用复制，旧日志和订单不会删除。

## 部署与验收

1. 按现有流程备份数据库与配置，拉取代码，编译前后端并重启。备份应能一致地还原 SQLite 数据及相关 WAL 文件。
2. 先对历史阻塞交易员执行“核对归档条件”，检查原账户订单证据和托管责任已完成收尾。若仍阻塞，按返回的具体账户、订单或查询错误处理，不直接删日志绕过。
3. 再启动原先受账户互斥影响的新交易员；历史交易员可保持停止或归档。
4. 复制开关保持默认关闭。需要复制时明确开启、查看预览并保存，随后手动启动；结果在编辑页“最近请求”中查看。

自动测试使用本地数据库、假执行器和 HTTP 测试服务器，覆盖原账户历史回执事故、账户及生命周期隔离、复制默认关闭、幂等登记、基线兼容、源仓变化、同方向多源部分成功、独立手动仓、提交与成交入账故障恢复。启动失败回滚还覆盖保留待执行请求、主动停止优先，以及过期回调不能停止新一轮运行。测试不向真实交易所下单。

复验命令：

```sh
go test ./... -timeout=5m
go vet ./...
go test -race ./store ./copytrade ./trader ./api ./manager -timeout=20m
```

前端在 `web` 目录执行 `npm test`、`npm run lint`、`npm run build`；构建命令包含 TypeScript 类型检查。并发检查在 SQLite 测试较多的机器上明显慢于普通测试，因此预留较长时限。
