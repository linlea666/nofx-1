# 退出回执与保护告警修复

## 根因

OKX 旧平仓接口把订单受理回执标为 `FILLED`，但没有返回成交数量。领航员退出链将这类回执保存为零成交的终态，又因终态时间戳跳过后续查单。固定减仓目标减去零成交，导致重复提交减仓。严格的源交易结算检查随后拒绝提交不完整证据，后续领航员全平被旧减仓阻塞。

保护维护又将“有退出订单等待对账”等同于“仍有待保护仓位”，反复重挂空仓的保护单。三种失败邮件分别去重且使用整点小时桶，导致同一故障跨类型、跨整点重复通知。

## 修改范围与复用

- `copytrade/order_evidence.go` 提取领航员退出、风险退出共用的查单逻辑；复用原客户端订单编号、交易所查询和成交数量账本。不确定回执不能授权下一笔订单。
- `store/copytrade_order_evidence.go` 扩展原回执更新：终态必须有相符的数量证据；同一证明用于退出、普通补仓、停止交易员和账户占用检查。确认的数量不会被迟到回执覆盖。
- 历史修正独立于下单：按原订单身份查询，修正前后保存到 `copy_trade_order_evidence_repairs`。已完成历史任务只更正证据和成交数量，不改变跟随进度或重放交易。活跃任务由原对账流程继续处理，后续源信号仍保留为待处理。
- 空仓事实与成交对账分离。新鲜持仓确认空仓、且没有可能迟到的开仓时，保护显示“已空仓·退出对账中”，停止重挂并清理原保护单；不伪造成交、不关闭源周期、不释放尚未核实的交易账目。
- `copy_guard_protection_incidents` 独立保存保护故障通知状态，复用现有异步邮件发送和发送结果回调；不把保护通知与领航员数据源故障状态耦合。

## 通知规则

无法建立保护、反复重挂、缺失超时共用同一故障记录。首次提醒后，只有严重程度升级或距离上次成功发送满一小时才再次提醒。跨整点与正常重启不重发。短暂挂单成功不足一分钟不会拆成新的故障；持续验证恢复后只发送一次恢复通知，且必须曾成功发出故障通知。

队列租约为五分钟，发送失败或队列不可用后至少一分钟再尝试。真正发送前再次验证周期、归属、保护状态和通知版本；已空仓、已结束或已恢复的旧故障邮件会被取消。SMTP 已接收邮件但进程尚未记录成功就崩溃的窗口无法做到严格一次投递，租约恢复后仍可能重复一封。

## 验证与上线

回归覆盖真实的无数量回执、查单超时/非终态/缺失数量/错误订单身份、重启、部分成交后取消、同方向多保证金模式、旧终态重复减仓记录、源全平排队、停跟、迟到开仓、空仓保护清理及通知去重与过期队列。

运行 Go 全量测试、相关包 race、`go vet ./...`，前端测试及 `npm run build`。部署前按现有流程备份数据库，由操作者拉取、编译并重启。新表兼容创建，不需要手工删除或修改旧订单。

启动和定期恢复仅通过原交易所订单查询补充旧退出证据，每轮最多扫描 25 个意图，循环游标避免某批过期记录挡住后续记录。交易所已无法返回的历史订单继续显示 `EXIT_EVIDENCE_PENDING`，不猜测修正、不重新下单。上线观察重点为未决退出数量、保护状态及两张新审计表；真实成交费用与盈亏仍使用既有独立结算账本。
