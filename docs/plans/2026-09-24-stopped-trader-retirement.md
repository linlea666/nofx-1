# 停止交易员的历史占用清退

## 根因与范围

账户互斥检查比旧归档逻辑更严格，两类历史记录可能留下无可用清退入口的占用：

- 保护单已由原对账逻辑标记为 `invalid`、所属周期已关闭，但新检查未识别这一终态。
- 旧平仓意图为 `FILLED / MAPPING_ALREADY_ACKNOWLEDGED`，源映射已关闭，却没有交易所终态字段。普通未完成意图对账不会再读取它，账户互斥仍将其视为未决提交。

本次仅调整账户占用判定和已停止交易员的归档准备。不改正常跟单、下单、止损、比例计算或盈亏账本，不直接删除历史数据。

## 复用与边界

1. 提取并复用账户启动、切换账户的同一保护单占用判定。仅当 `invalid` 保护单所属周期确已关闭、无待替换任务或旧替换身份时，才释放占用。其他未知或有效保护仍受原约束。
2. 扩展现有 `ReconcileStoppedTrader` 和停止清退事务，沿用“核对归档条件 → 删除/归档”入口，无新增前端流程。
3. 独立新增 `copy_trade_venue_retirements` 审计表：记录核对账户、运行代次、时间、原始意图及核验依据。当前空仓证明不等于历史成交证明，因此不补造交易所状态、成交数量或成交时间，也不改写原意图。

历史平仓清退要求：交易员完全停止；新鲜、完整、未缓存的账户持仓及普通/条件挂单查询均成功且为空；本地无未结持仓；同账户无其他运行中、启动中或停止排空中的交易员。账户及运行代次须与查询前一致；若保留着此前账户的占用记录，必须核对原账户，不能用修改配置后的新账户结果清退。

只接纳上述特定历史格式，并要求源映射已关闭、目标数量为零、无真实成交、无交易所订单身份、无现代订单尝试或成交提交。其他未决记录会使整个事务回滚。审计与原意图身份及更新时间绑定；出现新证据后不会继续豁免。重复核对、重启不会重复生成审计。

## 部署后操作

代码发布本身不会自动清理生产数据或发出交易指令。部署前按现有运维流程备份数据库，然后拉取、编译、重启。

1. 对需要移除的已停止交易员，使用现有“核对归档条件”入口；无阻塞提示时点击删除，将其归档并保留历史。
2. 已归档交易员无需恢复或再次删除；满足条件的历史 `invalid` 保护记录在账户检查中自动被正确识别。
3. 再手动启动新交易员。

若仍有仓位、普通/条件挂单、未知执行状态或查询失败，操作会保留阻塞和历史记录，不自动平仓或撤单。先核实对应原因，不通过删库绕过。

## 验证范围

- 历史平仓阻塞 → 交易所全空核对 → 归档 → 同账户新交易员启动。
- 重复核对及数据库重启后审计幂等，原执行记录所有时间、数量、金额不变。
- 新鲜度、账户、运行代次、同账户并发运行、有效持仓/挂单、接口失败及未知订单均不能误清退。
- 无归属、周期未结束、存在替换身份或替换任务的保护单不被当成已清理。
- 原停止清退、账户启动和切换账户回归，以及新增路径的并发检测。
