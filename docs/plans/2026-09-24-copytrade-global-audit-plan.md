# 跟单状态、总仓退出、Copy Guard 与结算统一修补方案

日期：2026-09-24。状态：用户已确认，按本方案实施；实现、验证和发布记录见 [实施交付说明](2026-09-24-copytrade-release.md)。

方案阶段只读取服务器运行版本、日志、数据库以及指定 OKX 订单/成交/仓位历史，并进行本地代码审查和离线重放。后续获得确认后实施本地代码修复。生产数据、配置及交易所订单不由本次开发操作修改，部署、重启由用户执行。本文不包含密码或 API 密钥。

## 1. 结论与调查边界

问题不能继续按“某个币种、某种 SKIPPED 原因”逐项补丁处理。共同根因是：

1. **执行意图已经终结，不等于源变化已经确认。** 两者分散写入，映射修订号可能仍停在原地，下一动作反复撞上旧指令。
2. **源周期、跟随参与状态、实际持仓、保护周期混在一起。** 原仓消失不代表领航员本轮结束；一个源子仓结束也不代表同方向实际总仓结束。
3. **已成交业务与保护补建、费用核实耦合。** 交易早已完成，仍可能因为缺保护周期或旧修订冲突长期对账，连带阻塞新动作。
4. **结算把不同含义的时间当作同一条硬边界。** 真实成交时间早于仓位记录创建时间 1 毫秒，就被当成无关成交过滤。
5. **健康检查没有覆盖这些跨表不一致。** 文件日志持续等待，页面却未明确显示对应阻塞；结算取证失败多数静默跳过。

生产范围扫描包括 29 个跟单配置，其中 7 个运行中；静态审查覆盖源读取、轮询、周期识别、执行意图、下单和对账、归属、减平、暂停恢复、风险保护、启动恢复、结算及 API/页面。生产账户目前均使用 OKX，其他适配器的兼容性需要在实施回归中验证，不能把静态审查当作其他交易所实盘验证。

以下区分“已经发生且有生产证据”“代码确认存在的触发路径”“尚未证明发生、但需回归覆盖的边界”。不把停止的交易员、正常暂停、正常风险退出或短暂等待统称为漏单。

## 3. 代码确认的同类触发路径

| 路径 | 问题 | 统一处理方向 |
| --- | --- | --- |
| 旧状态修复 | 仅匹配 close、归属释放、目标为零 | 改为按副作用事实分类，覆盖全部动作；不把 add 简单当 close 修 |
| 未提交指令被更新源替代 | 标记 SOURCE_SUPERSEDED，但 active 映射未消费对应变化 | 确认替代关系和源基线，在同一事务收尾 |
| 提交前失败后的动作变化 | canonical 不含 action，回收却要求 action 相同 | 先结束旧无副作用变化，再处理新变化，禁止依靠换 ID 绕过去 |
| 风险触发与排队加仓并发 | add 被 STOPPED_BY_RISK 跳过，后续减平占同修订 | 风险禁加仓与排队变化消费原子化；保留领航员退出权限 |
| 旧保护清理暂未完成 | OLD_PROTECTION_RETIRING 落为不可恢复 FAILED | 表达为前置条件待满足，清理后重验当前有效源状态 |
| 订单确认零成交 | EXCHANGE_TERMINAL_NO_FILL 没有统一源收尾 | 核实所有尝试终态后消费、替代或按当前策略重新评估 |
| 停止交易员、再启动 | TRADER_STOPPED_* 与映射未协调 | 停止时不交易；再启动区分既有参与轮次与未参与新轮次，不重发停止期间旧意图 |
| 旧已成交记录落后当前修订 | 先判冲突而跳过成交事实核验 | 成交去重入账，不回退映射，完成历史业务 |
| 交易完成后保护未完成 | 交易再次归为 RECONCILING | 交易完成、保护任务、结算任务分别推进 |
| 同方向多个源仓 | 已有本系统仓被误判为独立手动仓；忽略成员仍参与减仓分母；成员结束却终止总仓保护 | 引入统一方向跟随组，保留源成员身份和实际保护范围 |
| 自动启动恢复 | 未完整复用手动启动账户互斥 | 所有启动入口使用同一账户占用校验与运行代次 |
| 结算读取范围 | 从开仓一直查到现在，再逐订单验证模式 | 限定周期候选范围，无关后续订单不能阻塞已完成周期 |
| 健康和结算诊断 | 只覆盖部分未完成状态/数据源，错误静默跳过 | 共用异常分类器，记录阻塞阶段、证据和持续时间 |

乱序快照、缺页、同一快照同时减加、同毫秒多成交、配置热更新、分页游标停滞等纳入回归；没有事故证据的部分不冒充已发生原因，不顺带重写正常逻辑。

## 4. 保持不变的用户规则

| 场景 | 规则 |
| --- | --- |
| 已参与本轮，领航员减仓 | 同账户、实际合约、方向的当前总仓同比例减，包括手动仓及对应不同保证金模式 |
| 已参与本轮，领航员该方向全平 | 对应总仓归零后结束本次退出；反向仓不动，结束后不再处理后来新手动仓 |
| 首次参与前已有独立同向手动仓 | 整轮跳过，不开加减平、不自动接管保护 |
| 主动停跟 | 不跟随领航员交易，包括全平；原有保护继续 |
| 恢复 | 原周期及原仓连续性可确认才恢复，只跟随后续，不补暂停期间动作 |
| 止损/风险退出 | 本轮不自动开加仓；已参与轮次的后续领航员减平仍可处理同向总仓；旧止损不接管后来手动新仓 |
| 上线仍有漏跟仓 | 不追补、不重放旧平仓；核实当前状态并建立本轮跳过基线 |
| 手动改止损 | 允许收紧和放宽并持久保存，仍受独立强平安全边界约束 |
| 普通保护维护失败 | 告警和重试，不能改变已确认跟单成交；真实风险触发才执行风险退出 |
| 跟单比例与杠杆 | 保留原公式、系数和合约单位换算，不擅自降杠杆或改变仓位大小 |

保护旧单清理是新一轮风险增加的必要前置条件；不允许旧保护单可能伤及新仓时继续盲开。领航员减平不能被无关保护补建、费用核实或旧归属释放阻塞。

## 5. 统一设计

### 5.1 一个源变化收尾内核，分别表达交易、保护和账目

扩展现有事务函数，提取共同的身份检查、订单事实分类、成交去重和源确认部分，保留不同跟随状态的业务差异。

持久化区分：

- 源周期身份及本次源快照/变化；
- 变化是否已消费、被新变化替代或仍需重验；
- 指令是否真正提交、尝试是否终态、成交是否已入账；
- 跟随参与/暂停/跳过/风险禁加仓；
- 实际持仓连续性及保护维护；
- 历史费用核实。

不把这些压成一个泛化 `FAILED`，也不因为保护失败撤销已确认交易。

| 副作用事实 | 处理 |
| --- | --- |
| 可证明从未提交，临时前置条件未满足 | 保持可恢复等待；条件满足后重验当前源、控制版本和数量，不盲用旧决策 |
| 可证明从未提交，原变化已无效或明确应跳过 | 事务确认该变化的处置，释放预留，保留下一有效动作通路 |
| 全部订单尝试已终态且零成交 | 按当前源与控制规则收尾或重新评估，不永久占用修订，不假装成交 |
| 有部分/全部成交且订单事实完整 | 不可变成交只入账一次，提交业务结果，保留必要后续差量 |
| 存在可能已提交但未确定的尝试 | 原客户编号继续查单/查成交；保持未决并告警，禁止新编号盲重试 |
| 当前映射已比旧意图更新 | 核验旧成交是否已入账，只补缺失事实并收尾；不回退映射 |

确认源变化时，意图、源确认、映射修订与数量、必要预留释放在同一数据库事务完成。数据库提交失败必须可重试，不能忽略第二次写入错误。

原因码用于展示和历史兼容，不能继续充当“能否安全恢复”的唯一白名单。已提交客户编号和订单身份保持不变；不得删除旧意图、强改 FILLED 或使用 MAX(revision)+1 绕过未知成交。

### 5.2 源周期：证据不齐时不能把当前新仓写成旧周期

扩展现有 source lifecycle：区分“当时已确认的原周期”与“当前观察到的候选周期”，保留源平台、领航员、posId、开仓时间、快照证据和本地周期代次。

- posId 可复用，不能单独代表一轮。
- 旧 cTime 缺失时，先查原始源信号、首个执行意图及可核验历史；不能直接用当前 cTime 给旧映射补身份。
- 已确认旧仓结束、不同开仓时间、方向变化等共同参与换轮判断；轮询可能错过中间空仓，不能只靠数量由非零变零。
- 决策带周期与控制版本，提交前再核验；旧快照不得覆盖较新已确认状态。
- 完整、成功、可信的新鲜快照才能确认源归零；接口错误、缺页、非法值不能触发全平。
- 周期身份不明只阻止相应范围内无法证明安全的新动作，显示原因；不把整个账户所有正常币种统一判坏。

### 5.3 同方向跟随组：解决多源仓与总仓规则冲突

**建议采用的内部结构：**执行账户＋实际合约＋方向为控制范围，保存交易员、源平台、领航员和组轮次；组内保留每个源子仓及其独立源周期/修订/意图。不同领航员不能意外合并，运行账户互斥仍保留。

这是总仓减平规则的协调层，不是新的一套下单系统。

- 同一组已有本系统跟随仓时，新源子仓属于该组正常跟随，不能因为“看到了非零仓位”就当独立手动仓跳过。
- 初始独立手动仓检查、整轮跳过、暂停、恢复基线、风险后的禁止开加仓，按组一致处理。
- 一个源成员平仓只结束该成员；领航员这一方向整体结束才结束组。仍有实际仓时不因成员结束撤掉保护。
- 多源变化按同一成功快照固定计算基线。不能把本帧新加入的成员当作旧分母，也不能按逐条修改后的分母反复计算。
- 同组同快照的减少量汇总为一个退出批次：`本批减少比例 = 各旧成员减少量之和 / 前一已确认快照的源总量`，以首次提交前一次读取的跟随总仓固定本批退出数量，再按实际保证金范围量化。批次保存成员变化清单，成交及源确认统一去重提交。不能每个成员分别对执行时剩余仓位再次乘比例。例如源 A/B 各 100 同时变为各 50，跟随总仓 100，应共减 50，而不是两次减 25% 后只减 43.75。重启或部分成交只补这份固定预算的余额。
- 同一快照既有减仓又有加仓，保留成员动作；先处理退出，再在源和风险条件仍有效时处理风险增加。不把相抵净额为零理解为“什么都没发生”。快照无法提供的真实逐笔顺序不伪造。
- 组轮次一般表现为领航员该方向合计由零到非零再到零，但还需结合成员周期证据识别轮询遗漏的空仓间隔。
- 源轮次结束与实际保护结束分别记录。主动停跟后领航员全平，只记录源轮次结束、禁止恢复这个已经结束的源轮次；不自动平仓，也不撤掉尚存原仓的保护。
- 暂停与风险禁入是独立状态。风险退出后再暂停、再恢复，只解除暂停，不解除本轮禁止开加仓；所有开加仓和恢复入口统一检查这一点。
- 整轮跳过不能通过普通“恢复”变成接管独立手动仓。恢复资格仍须核对原组轮次、实际仓位连续性和控制版本。
- “先退出、后增加”只是执行顺序，不是组轮次证据。同帧旧成员全结束、新成员出现时，先基于完整快照判断组边界，不能因处理旧成员时临时数量为零就结束组或撤保护；无法证明真实空仓间隔且成员身份全部替换时，明确标记边界待核实。

**本次已经确认的语义细化：**

1. 页面同币种同方向的“停跟/恢复”作用于整个方向组，避免一个隐藏源腿暂停、另一个源腿却继续减同一个总仓。
2. 某保证金模式的风险退出使该组本轮停止开加仓；其他模式尚存仓位继续保留保护并跟随领航员减平，不因一个范围触发而额外强平其他范围。
3. 风险退出后，领航员在同一方向组尚未结束时又开新子仓，仍不自动买回；等这一方向确实进入下一轮。

采用逐源腿独立暂停、独立手动仓归属，需要虚拟份额账本，且无法直接满足同向总仓退出规则，因此不建议本次另建这套复杂账本。

### 5.4 总仓退出、成交对账与保护收尾分离

继续复用已有 LeaderExitPlan、分仓目标、客户编号、attempt、实时持仓及量化：

- 部分减仓目标在首次提交前固定；重试只补差量，不重复乘比例。
- 真正全平按实际合约、方向、保证金范围确认归零，检查本系统在途开加仓及迟到成交。
- 退出任务交易完成及源确认共同提交；保护清理、保护补建、费用核实作为独立后续任务。
- 仍可能作用于新仓的旧保护单必须核实清理完成，才能允许下一轮开仓；这不阻塞已经有效的减仓/全平。
- 已完成退出不能因后续重复空仓快照重新开启，避免后来新手动仓被旧任务关闭。
- 原跟随仓已结束时，禁止旧保护补建接管新手动仓；保留用户授权的本轮领航员减平权限，两者分别判定。
- 交易所回执不明不当作零成交。历史窗口查不到订单也不等于订单从未存在；保留未决证据，限制阻塞范围并告警。

### 5.5 Copy Guard 保持原价格与连续性，扩展组绑定

- 保留原手动止损修订、首仓锚点、冻结策略快照、强平安全线、价格合成及保护任务队列。
- 组协调跟随规则；保护仍按实际仓位连续性和保证金范围管理。同一实际仓不同时启动多套互相改价的保护。
- 增加组与现有 Guard 周期的绑定，不批量改写历史 cycle ID/leader_pos_id，不合并重算正常锚点。
- 单个源成员结束，不能让旧“映射缺失/孤儿周期”修复器关闭组内仍有效保护；启动恢复、custody、gap 检查都使用新绑定关系。
- 风险触发与排队加仓在同一控制版本下收尾：禁止本轮风险增加，同时消费已取消的无副作用源变化，使后续领航员退出可继续。
- 无有效强平价、普通保护挂单失败仍保留已有保护，显示待核实并重试；不伪造触发。
- 配置切换不回写已有周期冻结快照；新增默认值不能抹掉历史手动价格。
- 历史多个不同锚点覆盖同一个实际仓时，保留原始证据和交易所现有保护，暂停该范围互相覆盖的自动改价/补建并告警；不各自反复重挂，也不自动挑一份删除其他保护。真实保护触发仍按可核验的既有范围处理，并设置组风险禁入。

### 5.6 账户互斥与启动路径统一

手动启动、自动恢复、服务重启和版本迁移统一使用执行账户占用与运行代次检查。复用已有数据库账户互斥以及领航员退出/风险退出执行互斥，修补遗漏入口。

- 配置更换账户/领航员不得改写旧任务身份。
- 账户占用检查不只查询 RUNNING。停止的旧代次仍可能有未决提交或交易所保护单；取得新代次控制前须核实这些副作用及保护归属。组、订单和保护任务绑定原执行账户，不能用更换后的账户执行器查询或撤销旧账户订单。证据不足时限制受影响范围的新开仓，不自动接管或清除旧单。
- 发现冲突时明确阻止冲突运行者并展示原因，不静默选择一个管理未知仓位。
- 网络取证、账目和保护补建不占着交易收尾锁长时间等待；保持退出优先。
- 本次生产尚无同账户多运行者，不为了潜在并发重写全部调度系统。

### 5.7 历史修复独立、可审计、可重复执行

先由共同分类器生成修复清单，逐条记录意图、映射、源周期、成交/订单事实、跟随状态、拟采取动作及排除原因；正常下单路径不夹带猜测性数据修复。

- 覆盖全部动作及所有终态/未完成组合，不只扩大 close 白名单。
- 可证明无副作用的旧阻塞，按实际源身份和参与状态完成事务收尾；不能统一把映射置 closed。
- 可证明已成交并已入账的旧任务，仅终结重复业务对账；缺失成交事实先补去重账本，不补交易。
- 有未决交易所副作用、身份歧义或保护冲突的记录保持待核实，不删除或盲解锁。
- 已停止/归档交易员不自动激活；恢复启动只沿用当前有效规则，不下停止期间的旧单。
- 华创、木子等上线时仍存在的漏跟源仓，不追单，建立本轮跳过基线；已经参与的有效原轮次不能被一概转成跳过。
- 修复应用前再次校验运行代次、暂停版本、映射修订、源周期和订单事实；数据已变更则重算清单。
- 保存修复版本、证据摘要和前后状态；重启、重复运行不会再次改动已完成记录。

必须区分三类恢复：

| 恢复来源 | 行为 |
| --- | --- |
| 正常进程崩溃、服务重启 | 保留原参与权限和执行预算。已参与轮次、仍有对应仓位且最新可信源要求退出时，按当前状态完成有效减平；不能以“不追单”把源归零吸收成新基线而留下仓位 |
| 用户明确停跟后恢复 | 遵守不补暂停期间交易及原仓连续性要求；暂停期间原源轮次已结束则不能恢复该轮，原保护按实际仓位继续 |
| 一次性历史修复/升级基线 | 对未参与漏跟轮次或失去可信周期身份的旧记录不补开、不重放旧 close；已证明仍参与、仍有效的当前退出不得被这一政策屏蔽 |

交易员停止后不自行恢复运行；用户再次启动时按已保存的参与/暂停/风险状态判断当前有效动作。停止前排队意图不能直接重发，也不能把“关启交易员”一律当作“所有持仓已主动停跟”。

### 5.8 结算：候选时间范围与身份归属证明分开

复用 BuildPositionSettlement 和现有成交分配/费用修订账本，普通持仓与 Copy Guard 共用证明规则。

1. 原始 cTime/uTime 作为交易所周期证据保留，另保留真实首末 fillTime，不篡改为 ts。
2. 查询与候选筛选统一采用有界容差，复用现有一秒容差的设计；**时间接近不等于归属成立**。
3. 通过实际合约、方向、保证金模式、原始入场订单、唯一成交身份、完整从空仓到平仓的数量及毛净额关系，选出唯一可证明周期。
4. 候选窗口含相邻旧周期、新周期或同毫秒边界歧义，无法唯一确认就保持待核实；不能扩大窗口后把多轮拼起来。
5. 扩展历史查询的截止时间和分页完整性检查。接口时间过滤与真实成交时间含义分别处理，取得周期所需证据后，不让远期无关订单查不到阻塞旧结算。
6. 重复页按成交身份去重；同一身份内容冲突必须报错。成交缺失、错误保证金模式、净额不合、累计历史跨周期仍拒绝。
7. 本次三条 ZEC lot 要走完整读取、解析、模式核验、证明、Apply 链路，精确对齐数量、费用、真实时间与强平类型；重复同步不重复分摊。
8. 每个失败阶段保存可查询原因及重试状态。证据不足显示待核实，不用零费用或估计净值充当已核实。
9. 同毫秒跨订单开平不能依赖接口页顺序、稳定排序或人为“先开后平”。存在可信顺序证据时使用该证据；否则无法唯一证明周期就保持待核实。输入打乱、分页反序不应改变结论。
10. 原始 cTime/uTime 与真实首末 fillTime 分字段保存。周期去重身份和历史分页仍依赖原始交易所证据，不能因修正展示时间生成第二个 settlement 或再次分摊费用。

### 5.9 观测与页面：区分正常不跟与故障

使用与运行/修复一致的分类器，而不是前端另猜状态：

- 数据源：最后成功完整快照、数据新鲜度、错误/退避；
- 执行：阻塞意图、动作、源/映射修订、首次及最近等待、是否有未决订单；
- 跟随：参与、初始手动仓整轮跳过、主动暂停、风险禁加仓、周期身份待核实；
- 保护：策略止损、独立强平保护、交易所核验、清理/重试；
- 结算：已核实/待核实、所缺证据和失败阶段。

同一阻塞变化时记录事件，持续时限频告警；避免每秒重复相同文字撑满日志。已有订单提交、真实成交等时间指标继续保留，明确数据获取、决策、提交、成交分别耗时。

健康状态显示具体方向组及受影响动作，区分“不能新开”“退出待对账”“仅保护维护”“仅费用待核实”。单个旧周期异常不能把整个交易员标成无法跟单；停止/归档的历史候选不计入当前漏单数量。

跟单金额公式不变，继续展示权益、系数、目标名义金额、量化结果、实际成交、资金不足/量化差额。不能用“运行中”一项掩盖跟单状态异常，也不能把正常整轮跳过标成故障。

## 7. 兼容、迁移与实施顺序

采用兼容加表/加列和幂等迁移。原意图 ID、客户编号、成交账本、Guard cycle ID、冻结策略、手动价及锚点保留。

已有一对一记录可证明时绑定为单成员组；已有多个源记录指向同一实际仓，必须核实组轮次和保护身份。多套不同锚点同时覆盖同一实际仓时不能自动合并，保持已有证据和保护状态并报告冲突。

建议开发顺序是依赖顺序，不是“上生产试一点再看”：

1. 固化匿名事故样本和不变量测试，产出只读分类器与修复清单结构。
2. 实现共同事务收尾、旧成交核验、源周期身份。
3. 实现方向组、总仓退出、保护绑定和所有控制入口的一致性。
4. 接入独立历史修复与启动账户互斥。
5. 修正结算证据边界及分阶段诊断。
6. 更新 API/页面，并完成组合回归、并发和整体审查。
7. 全部通过后统一提交推送；用户自行拉取、编译、重启。

上线前重新生成当前数据修复清单；本次只读快照不是将来直接执行的 SQL。上线不会补开漏单或重放过期平仓。部署后的状态修复只能处理证据完整且通过版本校验的记录，其他记录明确待核实。

不把回滚理解为“把新状态交给旧逻辑继续跑”；涉及新增运行状态时，需先停止产生新指令并核实在途订单，再按兼容版本/迁移策略处置。实施交付时提供具体发布和恢复步骤，由用户执行。

## 8. 验收：覆盖状态组合，而非只增加事故单例

### 8.1 必须重放的真实样本

- 华创：旧 active revision=9 + SKIPPED add revision=10 + 新 cTime/复用 posId。
- 木子：旧释放 add 卡住，后续源增大/减小/归零分别验证。
- 原 ZEC/DOGE close 修复样本，确保本次不破坏已经有效的修复。
- 智能跟熬夜：旧成交修订落后当前映射，成交不能丢失或重复记账，后续正常动作不被永久阻塞。
- 停止交易员历史意图，重新启用不补旧单且不永久卡住。
- ZEC 14 条真实成交时间/数量、三个本地 lot、首单早 cTime 1 毫秒，全链路结算。

### 8.2 状态交叉与故障注入

| 维度 | 覆盖 |
| --- | --- |
| 动作 | 首开、加仓、减仓、全平、同向重开、反手、同一快照同时减加 |
| 执行阶段 | 预留、未提交、提交成功但回执丢失、终态零成交、部分成交、全成交未确认、确认完成但保护待维护 |
| 控制状态 | active、整轮跳过、手动暂停、恢复、风险禁加仓、原仓脱离、源结束、交易员停止/归档/重新启动 |
| 源身份 | 相同 posId 新 cTime、缺旧 cTime、缺新 cTime、源腿新增/退出、旧腿全被替换但总数量相同 |
| 持仓范围 | 手动加仓、原仓结束后同向手动重开、不同保证金模式、反向仓、同向多个源成员 |
| 外部异常 | 429、超时、错误空列表、缺页、重复页、乱序快照、查单暂时不存在、迟到成交、旧保护撤单失败 |
| 崩溃位置 | 下单前后、回执前后、成交入账前后、源确认前后、保护后续任务前后、迁移事务前后 |
| 结算 | 时间误差、同毫秒多成交、缺首单一笔、跨周期邻近成交、错误订单/模式、重复分配、后续无关订单查询失败 |

关键断言：

- 交易所副作用不明时不盲重发；任何重试、重启、重复快照不重复下单/减仓/费用。
- 已确认无效的源变化最终有明确处置，不永久占着下一修订；映射修订不回退。
- 部分减仓量固定，全平只在真实源全平及允许跟随时发生；反向不动。
- 正常初始手动仓跳过、暂停、恢复不追历史、风险后不买回、上线不追单都保留。
- 多源 A/B 的开、减、全平，不出现忽略 B 却用 B 稀释退出后结束 A 保护的残仓。
- 多源同帧各减一半时总仓恰减一半；部分成交和重启继续同一数量预算，不变为顺序相乘的 43.75%。
- 手动止损与锚点跨重启不变，真实强平边界有效；普通保护维护不改跟单成交结果。
