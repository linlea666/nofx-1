# 跟单统一修补实施与发布说明

本次按照用户确认的 [统一方案](2026-09-24-copytrade-global-audit-plan.md) 实施。服务器调查只读；本次开发未修改生产数据库、配置和交易所订单，未部署或重启。由用户拉取代码后编译、部署。

## 修复边界与复用

- **源变化收尾：**复用执行意图、订单尝试、逐单入账记录和映射修订；增加统一事实检查及事务收尾。显示为 FAILED/SKIPPED 不能代替“未提交、终态零成交、逐单已入账”的证明。未知回执继续对账；临时前置失败仍重验，已明确放弃的开加仓消费本次源变化，未完成减平不被吞掉。
- **历史修复：**保留原动作及订单身份，证据完整的旧状态幂等修复；旧映射缺失可信开仓时间时不认领当前 cTime。已参加且能够证明仍是原轮次的源关系保留后续退出权；无法核实的漏跟源仓建立跳过基线，不补开、不执行过期退出。
- **方向组：**以交易员、源身份、执行账户、实际合约、方向协调源成员。复用已有逐保证金范围退出和订单去重，固定一批减仓数量；暂停/恢复、风险禁开加仓按组一致。暂停、风险退出和源结束分别保存。整帧观测事务发布；同帧全部成员替换且无法证明组边界时仅暂停新的开加仓，保留有效旧退出。
- **保护：**复用已有任务队列、原周期和首仓锚点、手动止损及安全边界；正常保护维护不能把已完成交易重新标为未完成。共享实际仓范围只维护原保护；历史多锚点冲突明确待核实。无 custody 的老记录必须凭首单和完整实际成交证明连续性，不凭今天同向持仓补建保护。
- **运行隔离：**手动启动与进程恢复都核验执行账户；旧账户仍有归属或交易所义务不能随配置转移。启动失败记录实际生命周期，不能页面显示运行却没有跟单工作进程。
- **账目与诊断：**成交候选范围允许交易所记录时钟误差，但仍严格证明唯一完整周期、合约/方向/保证金模式及订单身份。结算去重使用原始周期身份，平仓时间使用真实成交。费用待核实独立于执行和保护。新增运行状态接口及面板，不把历史费用缺口当作当前漏单。

全量回归另外确认并修复同账目链路的日历边界问题：原本把服务器本地零点无时区写入 SQLite，导致 UTC+8 凌晨的成交不计入“今日”。现在保留服务器本地日历语义，传入明确时间边界，并兼容历史 SQLite/RFC3339 混合格式。

不改变跟单系数、比例公式、杠杆及合约单位换算；不加入本轮风险退出后的自动买回。

## 数据兼容和首次运行

使用兼容建表、加列和幂等初始化，保留原成交、保护周期、手动价和策略快照。新增表保存方向组/成员及退出批次、源收尾证据、运行异常、费用核查及执行账户声明。

自动修复必须满足逐订单副作用证据及当前修订校验。无证据的记录保留待核实；不会用删除历史记录、修改旧动作或重发旧订单解锁。历史修复与正常服务重启不同：当前仍有效的退出任务继续对账和执行，不能被上线跳过基线吞掉。

原交易员主动停止后的重新启动，只吸收停止期间已发生的开加仓，不追补；仍需完成的当前退出继续按退出规则处理。主动停跟的原仓及其保护仍遵守暂停状态，恢复只吸收暂停期间源基线。

## 验证记录

已通过全项目 `go test ./... -count=1 -timeout=10m`、`go vet ./...`，以及 `go test -race ./copytrade ./store ./trader ./api ./manager -count=1 -timeout=12m`。最后补充的预留恢复和首次平仓回调故障用例也单独通过普通测试和并发检测。前端 13 个测试文件共 141 项测试、ESLint、TypeScript 检查及 Vite 生产构建通过；最终格式与差异检查通过。核心新增回归覆盖：

- 华创、木子旧 add 卡修订；旧已成交任务与合法部分成交补量分开处理。
- 同方向多源同时减仓、部分成交、重启、源收尾数据库故障，不重复减量。
- 组观测半途失败回滚、暂停恢复完整成员校验、风险写库失败下同组内存拦截。
- 预留成功后的组绑定、周期证据或退出预算写入失败；连同恢复标记再次写入失败时也能恢复原订单身份，只处理本引擎确定尚未入队的记录，不回收正常在途任务。
- 原仓结束后手动重开不接管；旧 close 在首次成交回调及后续重试中，保护清理或结算启动失败均不倒退业务完成状态；未确认成交的补偿继续保留对账屏障。
- 账户启动冲突及失败后生命周期；原执行账户尚有归属/未决义务时禁止换绑。
- ZEC 14 条匿名真实数量与时钟样本，经接口解析、成交证明、三条本地持仓分摊及重复同步，净损益为 **-438.9382003 USDT**；保留真实首单早 cTime 1 毫秒的事实。
- UTC、UTC+8、UTC-5、纽约夏令时切换日的日/周/月边界，以及未知/失败状态的前端呈现。

## 用户部署和核对

1. 沿现有流程停止产生新交易指令，核实在途订单；备份生产数据库及当前部署版本。保留已托管的交易所保护单。
2. 拉取本次提交，按项目原有流程编译后端和前端、重启服务。兼容初始化由程序启动执行；不需要手工执行事故修复 SQL。
3. 查看运行状态面板和启动日志：华创、木子相关旧状态应出现明确收尾/本轮跳过依据；当前新轮次依正常逻辑处理。已有手动仓、主动暂停、边界待核实不可误当成新的漏单。
4. 核对 ZEC 结算是否取得足够交易所证据；资料完整时自动幂等补齐费用和类型，资料不足显示费用待核实。开发中的离线验证不等于生产数据库已经改正。
5. 核对现存手动止损价、首仓锚点和保护状态；存在保护冲突或身份待核实时按页面证据检查，不通过重复重启或强行重发旧单处理。

公开领航员数据仍可能延迟；本次不宣称仅靠轮询能够保证在任何市场变化中先于强平退出。

另一个展示口径保留现状：趋势图仍按 UTC 分日，日/周/月汇总按服务器本地日历统计。此次修复统计筛选时丢失时区的问题，没有顺带改变趋势 API 的日期含义；如需统一，应连同前端时区选择另行明确。

## 恢复原则

不要在新版本已经执行订单后直接恢复旧数据库，否则会丢失订单身份和成交去重记录。若需回退，先停止新指令、核对交易所未决订单和保护义务，保留新数据库及日志，再选择兼容恢复方式；旧程序不应直接接管新增方向组状态。本次不自动执行生产回滚。
